
## Where is the compute?
In AWS, **“compute” is the capacity that actually runs your code**—CPU, memory, networking, and often GPU/accelerator resources. It is physically hosted on AWS infrastructure in a chosen Region and Availability Zone, but exposed to you through services such as EC2, containers, and Lambda.aws.amazon.
## Where to find it

In the AWS Management Console, open the **Compute** category under **Services**. The most common choices are:

|Need|AWS compute service|What runs your code|
|---|---|---|
|You want a VM/server you control|**Amazon EC2**|An EC2 instance—AWS’s virtual server|
|You package your app as a container|**Amazon ECS** or **Amazon EKS**|Containers, running on EC2 or AWS-managed Fargate capacity|
|You want to run a function on events or HTTP requests|**AWS Lambda**|AWS-managed serverless execution environments|
|You want an easy small server/site|**Amazon Lightsail**|Simplified virtual private servers|
|You process queued or scheduled jobs|**AWS Batch**|Managed batch compute environments|

AWS categorizes its core compute offerings as **instances (virtual machines), containers, and serverless computing**.aws.amazon+1

## The simple mental model

- **EC2**: “Give me a computer.” You choose an instance type, operating system, network placement, storage, and software. An EC2 instance’s type determines the available compute, memory, network, and storage profile.[aws.amazon](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/concepts.html)
- **ECS/EKS/Fargate**: “Run my container.” You supply a container image rather than manage an individual server directly.
- **Lambda**: “Run this code when something happens.” AWS provisions and manages the underlying servers; billing is based on compute time while the code runs.[aws.amazon](https://docs.aws.amazon.com/whitepapers/latest/aws-overview/compute-services.html)
- **Batch**: “Run many non-interactive jobs.” Useful for workloads such as data processing, rendering, simulations, and other queued work.
## Physical location

Your compute runs in the **AWS Region** you select—for example, `us-east-1` or `us-east-2`—and generally in one or more **Availability Zones** within that Region. That location choice affects latency, data residency, service availability, and cost.

For a typical web product:
text
`User request    → Route 53 / CloudFront / Load balancer   → Compute: Lambda, ECS/Fargate, EKS, or EC2   → Data: RDS, DynamoDB, S3, ElastiCache, etc.`
So: databases store data, S3 stores objects, VPC provides networking, and the **compute layer executes your application logic**.

## Practical default

For a software builder starting a new workload:

- Choose **Lambda** for event-driven APIs, automation, short tasks, and low/variable traffic.
- Choose **ECS on Fargate** for always-on containerized web services without managing servers.
- Choose **EC2** when you need OS-level control, specialized hardware, long-running workloads, or particular networking/software requirements.
- Choose **EKS** when Kubernetes itself is an intentional platform decision—not merely because containers are involved.
    
EC2 remains AWS’s general-purpose virtual-server option, with configurations balancing compute, memory, networking, and storage; compute-optimized variants suit CPU-heavy workloads such as batch processing and media transcoding.

## Where is the database?
In AWS, there is no single “database” location. Your application’s database is usually a separate managed service—most commonly **Amazon RDS/Aurora** for SQL databases or **DynamoDB** for NoSQL—and it resides in the AWS **Region** you selected.
## Find it in the AWS Console

## If it is a SQL database

For PostgreSQL, MySQL, MariaDB, SQL Server, Oracle, or Aurora:

1. In the AWS Console, check the Region selector in the top-right corner.
2. Search for **RDS**.
3. Open **Amazon RDS** → **Databases**.
4. Click the database instance or Aurora cluster.
5. Open **Connectivity & security** to find:
    - The endpoint/hostname
    - Port
    - VPC and subnet group
    - Whether it is public or private
    - Security groups controlling access

RDS manages the database engine and operational tasks such as provisioning, patching, and backups.aws.amazon+1

Example connection string shape:

text

`postgresql://USER:PASSWORD@my-db.cluster-xyz.us-east-1.rds.amazonaws.com:5432/my_database`

The endpoint is the “where”; `my_database` is the logical database inside that server/cluster.

## If it is a NoSQL database

For DynamoDB:

1. Check the AWS Region in the top-right.
2. Search for **DynamoDB**.
3. Open **Tables**.
4. Your data is stored in a table rather than a server database instance.
    

DynamoDB is AWS’s managed key-value and document database service; you typically access it through the AWS SDK/API rather than a traditional host-and-port connection.docs.aws.amazon+1

## If you mean “where is my app’s data?”

Check these common places as well:

|What you are looking for|Likely AWS service|Console path|
|---|---|---|
|SQL tables, users, orders, app records|RDS or Aurora|RDS → Databases|
|Key-value / document app data|DynamoDB|DynamoDB → Tables|
|Uploaded images, PDFs, files|S3|S3 → Buckets|
|Cached sessions / cached API data|ElastiCache or MemoryDB|ElastiCache → Redis/Valkey caches|
|Analytics warehouse data|Redshift|Amazon Redshift → Provisioned clusters or Serverless|
|Secrets such as database passwords|Secrets Manager or Systems Manager Parameter Store|Secrets Manager → Secrets|

S3 is object storage, not a relational database, although many applications store their files there while keeping file metadata in RDS or DynamoDB.[docs.aws.amazon](https://docs.aws.amazon.com/)

## Important: check the Region

A frequent reason a database appears “missing” is that the console is set to the wrong Region. RDS databases are tied to a specific Region and, commonly, deployed across Availability Zones within it for resilience. AWS services list resources only in the selected Region.[aws.amazon](https://aws.amazon.com/products/databases/)

If you are looking at an existing project, the fastest path is usually:

text
`AWS Console → select likely Region → RDS → Databases`

Then check DynamoDB → Tables if RDS is empty.
